Fundamentos — Semana 07

Cuatro conceptos, un contenedor

Vocabulario para leer y diseñar configuración Spring sin confundir responsabilidades.

💉
DIDependency Injection

Patrón de diseño: la clase recibe desde afuera los objetos que necesita, en vez de crearlos con new.

🧱 Lego: te entregan los bloques listos; tú los unes, no fabricas el plástico.

En Spring: la dependencia llega por el constructor. Resultado: menos acoplamiento y tests más simples.

🏗️
IoCInversion of Control

Principio de diseño: el framework controla el flujo y la creación de objetos, no tu código.

🎬 Hollywood: “No nos llames; nosotros te llamaremos”.

En Spring: el ApplicationContext crea y conecta los beans. DI es una técnica para aplicar IoC.

🔗
wiringConexión de beans

Es el acto de conectar: decidir qué implementación concreta llena cada dependencia requerida.

🧩 Analogía: encajar la pieza correcta del rompecabezas en el hueco que le corresponde.

EmailSender (interfaz) se conecta con FakeEmailSender dentro de NotificationService.

🌎
profilePerfil de entorno

Una etiqueta de entorno (dev, prod) que activa solo los beans válidos para ese contexto.

🚦 Analogía: un semáforo que solo deja pasar al bean correcto según el entorno activo.

@Profile("dev") → fake; @Profile("prod") → SMTP real. Nunca ambos a la vez.

Cómo encajan en Spring (de principio a implementación)

Reglas de lectura
  • IoC es el principio: Spring toma el control.
  • DI es la técnica: entrega objetos desde afuera.
  • Wiring es la conexión: interfaz ↔ implementación.
  • Profile filtra qué implementación puede existir.
  • @Autowired pide a Spring resolver e inyectar un bean; constructor es preferido.

Wiring · Constructor

Inyección por constructor, siempre

Las dependencias se reciben en el constructor, nunca en un campo con @Autowired. Esto hace explícito qué necesita la clase y permite testear sin contenedor Spring.

⚠️ Problema: @Autowired en campo oculta la dependencia y dificulta crear la clase en un test unitario puro.
// ❌ hoy
@Autowired
private NotificationAuditLog auditLog;

// ✅ meta
NotificationService(EmailSender sender,
  NotificationAuditLog auditLog) { ... }
Profiles · Entorno

El entorno lo decide Spring, no un if

Cada implementación de EmailSender se anota con @Profile("dev") o @Profile("prod"). El bean correcto se activa solo, sin condicionales en el código de negocio.

⚠️ Problema: hoy un if (APP_ENV == "prod") dentro del servicio decide cómo enviar el correo — esto hace los tests impredecibles.
@Profile("dev") → FakeEmailSender
@Profile("prod") → SmtpEmailSender

NotificationService ← EmailSender (interfaz)
Estado actual — el if que debe desaparecer
String env = System.getenv("APP_ENV");
if ("prod".equals(env)) {
    // conectar SMTP real
} else {
    // solo loguear (fake)
}
Hoy transformamos NotificationService: recibe EmailSender por constructor y el entorno (dev/prod) lo resuelve Spring con @Profile, no un if.
Buenas prácticas para recordar
Constructor, no campoDependencias visibles y testeables.Ej.: sin @Autowired en atributos.
Un bean por perfilNunca dos beans del mismo tipo activos.Ej.: @Profile("dev") vs @Profile("prod").
Config por entornoProperties separadas, no hardcode.Ej.: application-dev.properties.
Tests con perfil fijo@ActiveProfiles hace el test determinista.Ej.: siempre usa el fake en test.
Sin red en dev/testNada de conexiones reales al correr tests.Ej.: FakeEmailSender solo loguea.
